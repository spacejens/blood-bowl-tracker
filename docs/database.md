# Database

How the PostgreSQL schema is migrated, how every table's history is
tracked, and how importers are re-run safely against a long-lived database,
with links to the pages describing how individual entities are stored. See
[architecture.md](architecture.md) for the package structure around it.

## Migrations

Migration SQL files live in `packages/db/migrations/` and are generated by drizzle-kit:

```bash
cd packages/db
pnpm db:generate --name add_players_table   # generates a new migration from schema changes
```

Always review the generated SQL before committing. Drizzle-kit may generate `DROP + ADD` for a rename — rewrite these as `ALTER TABLE ... RENAME COLUMN` / `ALTER TABLE ... RENAME TO` to preserve existing data.

Migrations are applied automatically at application startup. `createDb` in `packages/db` calls `drizzle-orm`'s `migrate()` before returning the database instance, so every deployment applies any pending migrations before the app begins handling requests. Migrations are roll-forward only; there is no rollback mechanism.

Production runs two machines that can start at the same moment (a deploy, an
app restart), and drizzle's `migrate()` takes no lock of its own, so both could
see the same migration as pending and apply and record it twice. `createDb` therefore runs
the migrations under a Postgres advisory lock (key `4242`/`2`, distinct from the
leader-election lock's `4242`/`1`) held on its own single connection. A second
machine waits for the lock, then finds nothing left to apply. The lock is
released when migrating finishes or fails, and Postgres frees it if the machine
crashes or loses its connection.

### Changing data in a long-lived database

The production database is never dropped. It is backed up daily and before
every deploy (see [Database backups](discord-bot/production-backups.md)), so a
change has to reach the data already there rather than rely on a rebuild. Each
kind of change has one route:

- **A migration** in `packages/db/migrations/`, for every schema change and for
  every fix to existing rows that is not hand-curated data (a backfill, a
  corrected value in importer-sourced data, a re-keyed row). It runs once per
  database, at startup.
- **A [manual batch](import-manual/batches.md)**, for all hand-curated data,
  including a correction to a curated value that is already in the database: a
  new batch applied once, never an edit to a batch a database already holds,
  and never a migration.
- **An importer**, only for what its source system sends. It creates and
  updates rows from that source and never repairs rows the source no longer
  describes (see [Re-running importers](#re-running-importers)), so it is never
  the way to correct existing rows.

A migration that corrects an importer-sourced value which is also a Name
external ID adds the corrected spelling as an extra Name external ID on the
same row and keeps the old one, skipping it when another row already holds
that spelling. Name IDs are matched by exact string, so this lets the
importer, which now produces the corrected spelling, find the row again
instead of creating a duplicate, without merging two rows. If the spelling
was already held by another row, a later import that sends a source id
belonging to the first row can then fail loudly with an upsert conflict
rather than corrupt data, so check for such collisions with a read-only query
before deploying. The `fix_bbl_windows_1252_text` migration is an example.

Because tracked rows cannot be deleted (see [History tracking](#history-tracking)),
a fix that retires a row flags it rather than removing it, as
[Curated sets that shrink](#curated-sets-that-shrink) does.

Migrations are roll-forward only, so a migration that damages data is not
undone by reverting it: fix forward with another migration, or restore the
backup taken before that deploy (see
[Restoring a backup into production](discord-bot/production-restore.md)).
Re-importing everything is not a way to apply a change.

## History tracking

Every table in `packages/db/src/schema` — both the `game_data` schema
(`packages/db/src/schema/game-data/`) and the `discord_bot_usage` schema
(`packages/db/src/schema/discord-bot-usage/`, see `packages/discord-bot-usage`
in [architecture.md](architecture.md#toolapp-relationships)) — is built with `historyTrackedTable()`
(`packages/db/src/schema/history.ts`), not a direct `<schema>.table(...)`
call. It automatically adds `created_at`, `updated_at`, `history_version`,
and `history_period` columns, derives a companion `<table>_history` table
that mirrors the tracked table's _current_ columns (name, type, and
nullability), and registers the table so `pnpm run db:generate` can finish
its DDL automatically.

Adding a new table therefore only requires calling `historyTrackedTable()`
instead of `<schema>.table()` — running `pnpm run db:generate` once produces
a single migration with the table, its history companion, and both its
triggers (the temporal-tables `versioning()` trigger and a
`set_updated_at()` trigger) together. A completeness spec
(`packages/db/src/schema/history-completeness.spec.ts`) fails CI if a table
is ever added without going through `historyTrackedTable()`.

Writing to a history-tracked table must go through a plain `insert` or
`update`, never `INSERT ... ON CONFLICT` — neither `DO UPDATE` nor
`DO NOTHING`. `versioning()` is a `BEFORE INSERT` row trigger installed to
include the current version in history, so it writes a history row for the
attempted row before Postgres even checks for a conflict. When the row does
conflict, that history row cannot be kept, and the whole transaction aborts:

- If the attempted row drew a fresh serial id, its history row references a
  tracked row that never comes into existence, so the history table's
  deferred foreign key to the tracked table fails the transaction at commit
  (`23503`).
- If the attempted row reuses an existing id (`ON CONFLICT (id)`), its
  history row collides with that id's existing history row on the history
  table's `(id, history_version)` primary key, and the statement fails
  immediately (`23505`).

Either way nothing is persisted — no orphaned history row is left behind —
but the enclosing transaction can never commit a conflicting row this way,
and when it drew a fresh serial id that id is consumed. `packages/game-data`'s
`upsertByExternalIds` and `packages/discord-bot-usage`'s
`selectThenUpsert` (like the other natural-key writers in
`packages/game-data`) both select the row first
and branch to a plain `insert` or `update` for exactly this reason. These
outcomes are pinned against real Postgres by
`packages/game-data/test/history-tracked-conflicting-insert.e2e-spec.ts`.

`db:generate` post-processes the generated `migration.sql` for history
tables: a brand-new `<table>_history` is created with
`CREATE TABLE (LIKE "<schema>"."<table>")` (copying columns/types/NOT NULL
but not the tracked table's PK, FKs, defaults, or identity), and its
primary key `(id, history_version)` plus a deferrable self-referencing FK
back to the tracked table are appended directly. When a tracked column is
removed, the corresponding history-table `DROP COLUMN` is rewritten to
`ALTER COLUMN ... DROP NOT NULL`, so the column survives as nullable and
old history rows are preserved. Only future migrations are affected;
existing migrations are never rewritten.

Postgres fires same-timing triggers on a table in alphabetical trigger-name
order, so `<table>_set_updated_at` always fires before `<table>_versioning`
(`s` < `v`) — this ordering is required, not incidental, and the trigger
names are deliberately left unprefixed to keep it. `set_updated_at()`
(`packages/db/sql/set_updated_at_function.sql`, not vendored) is
conditional: it skips the `updated_at` bump when `NEW IS NOT DISTINCT FROM
OLD`. Because it fires first, before anything else has touched the row,
that comparison is a true "did the caller's `UPDATE` actually change
anything" check — it bumps `updated_at` only on a real change, and leaves
it untouched on a genuine no-op update.

`versioning()` then fires second and sees the row exactly as it will be
written: for a no-op, `NEW` is still identical to `OLD` in every column
(including `updated_at`), so its own built-in no-op guard
(`IF NEW IS NOT DISTINCT FROM OLD THEN RETURN OLD`) correctly skips writing
a history row; for a real change, `updated_at` has already been bumped, so
the history row `versioning()` inserts for the new "current version" (it
inserts using `NEW`) correctly captures the fresh timestamp rather than a
stale one. Both triggers always return `NEW`/`OLD`, never `NULL`, so
`UPDATE ... RETURNING` always returns the row, no-op or not — important
because `packages/game-data`'s upsert methods rely on getting a row back
from `RETURNING` on every update they issue.

Reversing this order (making `versioning()` fire first, e.g. via a `0_`
name prefix) was tried and rejected: `versioning()`'s history `INSERT` uses
`NEW` at the moment it runs, which would then be _before_
`set_updated_at()` had bumped anything, so a genuine update's new history
row would capture the row's _previous_ `updated_at` instead of its current
one — confirmed via manual testing. The 29 tables that predate this fix
only needed `set_updated_at()` replaced (`CREATE OR REPLACE FUNCTION` is
safe to re-run everywhere), via the
`20260717130000_make_set_updated_at_conditional` migration; their trigger
names and firing order were already correct.

The `versioning()` trigger function is vendored unmodified from
[nearform/temporal_tables](https://github.com/nearform/temporal_tables) at
`packages/db/vendor/nearform/temporal_tables/versioning_function.sql`, checksum-
tested to catch accidental edits. Upgrading it means replacing the vendor
file, updating the checksum test's recorded hash in the same commit, and
generating a new migration that copies the updated file's content verbatim
(the function uses `CREATE OR REPLACE`, so this is safe to re-run in any
environment, including production). Vendored components (currently just
this one) are tracked in `packages/db/vendor/vendored_software.md`.

Because history rows are written on insert (not only from the first
update onward), every tracked row has a referencing history row from the
moment it's created — so deleting a tracked row is always blocked, not
just rows that have accumulated history. This is intentional and
permanent: there is no supported way to hard-delete a tracked row.

### Curated sets that shrink

Because a tracked row cannot be deleted, a curated set that loses a member is
synced by flagging rows, not deleting them. The three trophy award rule tables
(`trophy_award_rule_match_event_types`,
`trophy_award_rule_excluded_match_event_types`,
`trophy_award_rule_eligible_positions`) carry a `removed` flag.
`TrophyRuleCurationSyncService` in `packages/game-data` inserts a newly curated
row, sets `removed` on a row the curation no longer lists, clears it when the
curation lists that row again, and writes nothing for an unchanged curation.
Every reader filters on `removed = false`.
`position_rules_set_skill_categories` uses the same `removed` flag, synced by
`PositionRulesSetSkillCategoriesService`.

## Re-running importers

The importers run repeatedly against a database that is never dropped, so
every write path is safe to repeat:

- A record re-sent with the same external IDs updates its row in place; one
  that matches nothing creates a row. No import ever deletes a row.
  The one exception is a position's skill categories, a set that can shrink
  on re-import: both TP's official team list import and the manual import
  flag a category `removed` when their source stops listing it.
- An unchanged re-run writes nothing: no `updated_at` bump and no history row
  (see [History tracking](#history-tracking)). This is pinned against real
  Postgres by `packages/game-data/test/importer-rerun.e2e-spec.ts` and
  `trophy-rule-curation-rerun.e2e-spec.ts`; the whole `apply 001-initial-seed`, source,
  plain `apply` sequence is run twice by
  `tools/import-manual/test/importer-double-run.e2e-spec.ts`.
- A row a source system drops or re-keys stays. It is fixed by a data
  migration or a once-applied [manual batch](import-manual/batches.md), never by an importer.
- Curated names belong to `tools/import-manual`. A source importer sets a
  coach, competition, skill, position, team or race name only when it
  creates the row (see
  [imports](api/imports.md#upserts-overlay-they-do-not-replace)).
- Importing from scratch into an empty database is the last-resort recovery
  path, for when no usable backup exists;
  [restoring a backup](discord-bot/production-restore.md) comes first. A
  create still takes the source's name, so a scratch import ends in the same
  state as a long-lived database, where a merged row keeps the name it was
  created with (or the curated one) rather than the last source's spelling.
  A scratch import runs the BBL and TP importers twice, before and after the
  remaining manual batches, because they read the advancement costs those
  batches supply (see
  [batches](import-manual/batches.md#operating-procedure)).
